# WinPilot 现状评估与改进路线（2026-06-27）

> 本文是一次完整技术审计的结论，给接手的 AI/开发者做技术决策用。
> 结论基于真实代码（含 file:line 证据）+ 2026 业界 SOTA 调研。
> 当前分支 `feat/winpilot-agent`，已推送到 GitHub。

## 一句话结论

核心思路（多维感知融合 + 动作级 expect 验证 + done 二次核验 + cache 友好的 append-only 上下文）**不落后**，对 computer-use 的硬问题做得比多数同类扎实。真正拖后腿的是**工程结构债**：把大量任务场景启发式硬编码进 1300/1700 行的核心文件，缺状态机抽象与上下文压缩。**方向对，结构需要还债。**

## 二、在 2026 业界格局中的位置

电脑操控当前分三类路线：
- 商用闭源：Claude Computer Use/Cowork、OpenAI Operator（已并入 GPT-5/Atlas）——纯截图+鼠标键盘，无 OS 依赖
- **开源原生模型：UI-TARS（字节）**——单一端到端模型，纯截图感知，OSWorld SOTA
- 编排框架：Browser Use、OpenClaw、Hermes——通用 LLM + 工具编排

**WinPilot 属于第三类，但感知比同类强。**

关键事实：OSWorld 2.0（108 个真实跨应用工作流）前沿模型成功率仅 **20.6%**——长任务不稳定是全行业未解难题，不是 WinPilot 独有。

感知路线之争的 2026 共识是 **hybrid 最优**：纯 a11y 树在很多应用上崩（树残缺），纯视觉浪费算力。WinPilot 的 UIA+Win32+OCR+CV+VLM 五维融合正是被推崇的方向——**这是真实优势。**

## 三、可借鉴/照搬的东西（按性价比）

1. **经验召回升级为语义向量**（1-2 天，最高 ROI）
   现状 `memory/experience.py:199-218` 是关键词+bigram 字符串重叠匹配。改用 embedding + 余弦相似度，"打开浏览器搜索"能召回"用 Chrome 查资料"。强化差异化护城河。

2. **借鉴 UI-TARS 的 System-2 显式反思**
   每步行动前写一段反思再决策（非隐式 CoT）。提升长任务成功率。WinPilot 已有经验/录制骨架，可升级成"记录失败+反思"。
   ⚠️ 警告：ProCUA 研究发现人类演示轨迹直接做 SFT 会**负迁移**（OSWorld 分数反降）。WinPilot 的人类演示录制若想喂训练，要避坑。

3. **Claude 的"可移植工具"设计**
   screenshot+click(x,y)+zoom 纯坐标接口、零 OS 依赖、可跨 VM/容器。WinPilot 刚移植的 screenshot/zoom/click 已是这形态，方向对；若要跨平台可继续抽象动作层。

## 四、缺点（基于真实代码，按严重度）

1. **业务启发式爆炸侵入核心循环**（最伤可维护性）
   `loop.py:44-337`（~300 行）是 `_is_drawing_task`/`_is_gui_only_task`/`_is_communication_task` 等正则任务分类器 + 阻断器；`_verify_done`（loop.py:773-1040，**268 行**）把通用核验和绘图/搜索/通信/文本 4 类专属校验耦合在一起。新场景=改核心循环，回归风险高，无法被 prompt/配置驱动。

2. **`tools.py` 1702 行 + 反射 dispatch**（超 800 行红线）
   schema+清洗+~50 个 `_t_` handler 混一个文件。建议按域拆 `tools/{perception,action,file,clipboard,memory}.py`，dispatcher 改显式注册表。

3. **上下文管理是"丢弃"不是"压缩"**（loop.py:467-485）
   字符阈值折叠（48000 chars）、无 token 预算、无语义摘要、无检索回填。长任务（max_steps 40）中段信息直接丢失。

4. **done 核验 fail-open + 每次额外 LLM 调用**（loop.py:1020-1027）
   judge 出错/JSON 不可解析即放行，可能掩盖真失败（为防死锁的取舍）。每次 done 多一次 LLM 调用（_JUDGE_MAX_TOKENS=2500），延迟+成本叠加。

5. **缺 lint/dead-code CI**
   本次审计发现 3 处确凿死代码（已修：fusion.to_text、tools._t_list_windows 各重复定义、_CLEAN_PROPERTY 重复键）。应把 dead-code 检查纳入 CI。

性能瓶颈：首次 observe ~12s 暖机（OCR/VLM 懒加载，可启动预热）；`read_text`（tools.py:1304）无条件叠加 OCR，绕过了 fusion 的 OCR 短路优化。

## 五、务实优点（别丢）

- DeepSeek prefix-cache 友好（append-only + 延迟折叠 + 计划只注入一次）——真实成本优化
- Stop 可中断在途 LLM 调用（loop.py:540-548）
- done 二次核验 + 动作 expect 验证——computer-use 核心难点，做得比多数 demo 扎实
- 五维感知融合 + UIA-rich 短路（跳过 OCR/VLM）——hybrid 路线 + 性能取舍兼顾

## 六、若只做 3 件事

1. 拆 `tools.py`（半天，纯重构，过红线了）
2. 经验召回上 embedding 语义匹配（1-2 天，护城河强化）
3. 加轻量 System-2 反思（借鉴 UI-TARS，提升长任务成功率）

**不建议**：追原生 GUI 模型路线（无数据/算力，ROI 极低）。护城河应是"强混合感知 + 经验学习 + 人类演示录制"组合。
